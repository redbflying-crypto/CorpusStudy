# CorpusStudy build plan

A personal Bible study chatbot with three layers:

1. **Corpus.** Public-domain Bible texts and commentaries, ingested and checksummed.
2. **Knowledge.** A curated, version-controlled knowledge bundle in **Google's Open Knowledge Format (OKF) v0.2**. It holds books, themes, people, doctrines and events, drafted by Claude and reviewed by a person.
3. **Answering.** A router, hybrid retrieval and Claude for generation, followed by a citation validator that checks every Scripture reference and every knowledge source before an answer goes out.

This plan replaces the earlier seven-phase plan. Work already done is kept wherever it still fits; the "Status" line under each phase says what is reused and what changes.

Reference: [OKF v0.2 SPEC.md](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md).

## How OKF is applied

OKF is the format of the knowledge layer only. The Bible texts and commentaries stay as data files (`data/processed/*.jsonl`). The bundle refers to them through `sources`, so every curated claim can be traced back to a text.

### Bundle layout (`knowledge/`)

```
knowledge/
  index.md                  # root index, frontmatter `okf_version: "0.2"` (the only frontmatter allowed)
  log.md                    # dated change history, newest first
  books/        index.md  genesis.md  romans.md  ...
  themes/       index.md  covenant.md  grace.md  ...
  people/       index.md  abraham.md  paul.md  ...
  doctrines/    index.md  justification.md  election.md  ...
  events/       index.md  exodus.md  resurrection.md  ...
  references/   index.md
    sources/    kjv.md  lsg1910.md  calvin-lcc.md  henry-concise.md   # one concept per source work
```

Rules:
- A concept's identity is its path, e.g. `doctrines/justification`. There is no `id` field.
- `index.md` and `log.md` are reserved names and are generated by tooling. Every other `.md` file is a concept with frontmatter.
- Concepts link to each other with standard Markdown links, preferably bundle-absolute ones such as `[faith](/doctrines/faith.md)`. No `[[wikilinks]]`.
- The bundle is versioned in git. Every draft, review and correction is a commit and is summarised in `log.md`.

### Concept frontmatter: the OKF core plus project keys

```yaml
---
type: Doctrine                        # OKF required. Project vocabulary below
title: Justification by Faith         # OKF recommended
description: God declares sinners righteous through faith in Christ alone.
tags: [soteriology, reformation]
status: draft                         # OKF lifecycle: draft | stable | deprecated
generated: { by: corpusstudy/drafter-1, at: 2026-10-23T10:00:00Z }
verified:                             # added only by the human review step
  - { by: "human:<your-id>", at: 2026-10-25T09:00:00Z }
sources:                              # OKF provenance; ids are footnote keys
  - id: henry-rom3
    resource: /references/sources/henry-concise.md#Rom.3.21-Rom.3.26
    title: Matthew Henry on Romans 3:21-26
    author: "human:matthew-henry"
  - id: calvin-gal2
    resource: /references/sources/calvin-lcc.md#xi-p12
    title: Calvin on Galatians 2:16
# project keys (OKF allows producer extensions)
title_fr: La justification par la foi
aliases: [justified, imputed righteousness]
key_passages: ["Rom 3:21-26", "Rom 5:1", "Gal 2:16"]   # validated against KJV numbering
tradition: reformed
other_views: true                     # the body has a "Where other traditions differ" section
---

# Definition
Justification is God's legal declaration ...[^henry-rom3]

# Reformed view
...[^calvin-gal2]

# Where other traditions differ
...

# Key passages
...

[^henry-rom3]: Matthew Henry on Romans 3:21-26
[^calvin-gal2]: Calvin on Galatians 2:16
```

**Type vocabulary.** OKF types are free text; ours are `Bible Book`, `Theme`, `Person`, `Doctrine`, `Event` and `Reference` (for source works). The consumer still accepts unknown types, as OKF requires.

**Actors** (OKF section 7):
- Claude's drafts: `corpusstudy/drafter-<n>`.
- Scripts: `process:<name>`, e.g. `process:okf-validate`.
- Your reviews: `human:<your-id>`.

**Trust tiers** (OKF section 5.3), derived from `verified`, decide how the bot uses a concept:

| Tier | Meaning | Use in answers |
|---|---|---|
| unverified | Claude's draft, not reviewed | Excluded by default (`CORPUS_USE_DRAFTS=false`); if enabled, labelled "unreviewed" |
| machine-confirmed | Passed the automated checks only | Same as unverified |
| human-reviewed | You signed it off | Used as the bot's Reformed position statements |

**Provenance.** Every interpretive claim in a concept body carries a footnote keyed to a `sources` entry. Each entry points at a specific Calvin or Henry excerpt id, or at a Bible passage. The citation validator resolves these footnotes, and a footnote that doesn't resolve fails validation.

**Not used:** OKF's Attested Computation (section 10) is for computed figures and doesn't apply. `stale_after` is optional, because doctrine doesn't expire.

### Two levels of OKF checking

- **Consumer (tolerant, as OKF requires).** Loads any OKF v0.2 bundle. It never rejects unknown types, unknown keys, missing optional fields, broken links or missing `index.md` files.
- **Producer profile (strict, for our own bundle).** Enforces our rules on our bundle: conformance, our type vocabulary, valid `key_passages`, every footnote resolving to a `sources` id, every `sources` entry resolving to a real excerpt, a bilingual `title_fr`, and no `[[wikilinks]]`. It runs in the tests and as `python -m corpusstudy.okf check`.

### Review workflow (the human gate)

1. Claude drafts or edits concepts on a branch, with `status: draft` and `generated: {by: corpusstudy/drafter-1}`.
2. The producer profile check must pass.
3. You review: either in a GitHub pull request, or here in chat.
4. On your approval, `python -m corpusstudy.okf verify <paths> --by <your-id>` adds `verified: {by: human:<your-id>, at: now}`, sets `status: stable` and writes a `log.md` entry. That becomes the commit you approve.
5. Any later content edit updates `generated.at` and moves the concept back to `draft` until it is reviewed again.

- **Claude:**

  - Generators for `index.md` (per directory, with descriptions from frontmatter) and `log.md` (dated entries).
  - CLI commands: `check` (conformance and producer profile), `index` (rebuild indexes), `verify` (the human sign-off stamp) and `log`.

  - Seed `references/sources/` with one `Reference` concept per source work, generated from `data/processed/manifest.json`. Each holds the edition, licence, checksum and excerpt-id scheme, and the source concepts are themselves stamped `verified: process:ingest`.
  - Tests:
    - **Conformance:** every non-reserved `.md` file has frontmatter with a non-empty `type`, and the reserved files follow their required structure.
    - **Round-trip:** unknown keys survive a load and save.
    - **Tolerance:** broken links and unknown types load without errors.
- **Exit:** `python -m corpusstudy.okf check knowledge/` passes; the bundle opens cleanly in any Markdown viewer.

### Phase 4: Chunking, indexes and hybrid retrieval
- **Claude:**
  - **Chunking:**
    - **Bible:** verse windows per translation, in each translation's own numbering.
    - **Commentaries:** split by excerpt, with long excerpts split further by size.
    - **OKF concepts:** split by heading, keeping frontmatter metadata (`type`, `tags`, `key_passages`, trust tier, `status`) for filtering.
  - **Keyword index:** SQLite FTS5 (BM25), one index per language.
  - **Dense vectors:** this depends on your embeddings decision, because the Hugging Face model downloads are blocked from my workspace:
    - (a) the Voyage AI API with your key;
    - (b) allow Hugging Face so a local model can be used;
    - (c) start keyword-only and add vectors later.
  - **Fusion:** reciprocal rank fusion of the keyword and dense results.
  - **Passage boost:** a reference in the question (e.g. "Romans 9") boosts chunks whose refs overlap it, using the KJV↔LSG map so it works in both languages.
  - **OKF-aware retrieval:**
    - Concept search filters by trust tier: human-reviewed only, unless `CORPUS_USE_DRAFTS` is set.
    - It follows one hop of links from the best-matching concept (for example from justification to faith).
    - The `index.md` files serve as a table of contents the router can browse.
- **Exit:** a retrieval test set (about 30 queries in English and French with expected passages) meets its recall target.

### Phase 5: Knowledge drafting and review
- **Claude:**
  - Draft about 36 concepts in OKF: 10 books, 8 themes, 8 people, 6 doctrines, 4 events.
  - Each concept is written from Scripture plus retrieved Calvin and Henry excerpts. Every interpretive claim is footnoted to a `sources` entry, `key_passages` are validated, and each has a French title.
  - Where traditions differ (election, baptism, the Lord's Supper, perseverance), the body has a "Where other traditions differ" section, so tradition is never presented as Scripture.
  - Each concept passes the producer profile, gets indexed and is logged.
- **Gate (you, the biggest human task):** review each concept for accuracy and Reformed faithfulness, then approve it (the `verify` stamp) or ask for changes. Batches of 6–8 per pull request keep this manageable.
- **Exit:** every concept is human-reviewed (`verified` by `human:<your-id>`, `status: stable`).

### Phase 6: Router, generation and citation validator
- **Claude:**
  - **Router:** sends each question to verse lookup, knowledge, retrieval or a combination, with a pastoral route that checks for crisis, abuse or self-harm first. It detects the question's language and answers in it.
  - **Generation:** answers use the Anthropic API with a system prompt that sets the Reformed framing, labels interpretation as interpretation, and briefly notes other views where the knowledge concept says they differ.
  - **Citation validator:**
    - Every Bible reference must exist in the answer language's translation and numbering.
    - Every quotation must match the corpus text.
    - Every knowledge claim must trace to a concept whose footnotes resolve.
    - Answers that fail are repaired or refused.
  - **Answer object:** carries the citations, the sources and, for each knowledge concept used, its trust tier.
- **Exit:** the validator's offline tests pass and a smoke test against the live API passes.

### Phase 7: API, chat page and evaluation
- **Claude:**
  - A FastAPI `/chat` endpoint.
  - A simple chat page that shows citations, which sources were used, and a trust badge on knowledge it drew on (reviewed or draft).
  - An evaluation set of 50+ questions: English and French, lookups, doctrine, people, history, cross-tradition questions and the safety cases.
- **Gate (you):** check the expected answers and the safety-sensitive cases.
- **Exit:** the evaluation targets are met (citation accuracy 100%, correct routing, safety cases handled).

### Phase 8: Docker and running locally
- **Claude:** a Dockerfile and docker-compose setup with the corpus and indexes in a volume and `.env` for secrets, plus a runbook covering rebuilding the corpus, re-indexing, reviewing concepts and updating the bundle.
- **You:** run `docker compose up` on your machine.
- **Exit:** the chat works locally from a clean checkout.

### Phase 9 (optional): Maintaining the knowledge base
- **Claude:** when the bot finds a gap (a question with no good concept), it drafts a new OKF concept as `status: draft` on a branch for you to review, never auto-published. It also runs a periodic `okf check` with link and coverage reports, and adds `log.md` entries.
- **You:** review the proposed concepts like Phase 5.
